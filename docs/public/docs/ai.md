This document is for AI assistants (Claude, Gemini, ChatGPT, and others) generating code with TypedCSS. When writing TypedCSS code, **always** follow the rules and patterns described here.

## Critical Rules (Quick Reference) [#critical-rules-quick-reference]

The complete rule set, distilled. Each rule is explained with examples in the sections below.

**MUST:**

* Call `css.create()` at module top level, never inside a component. (→ Forbidden Patterns)
* Bind styles with the `sx` prop, not `className`. (→ Mental Model)
* Import `@typedcss/css` in every file that uses TypedCSS styles, including files that only consume imported styles. It is required in a file that passes a style to a component through a prop other than `sx`, and safe and fastest everywhere else. (→ Core Usage)
* Start nested selector keys with `:` (pseudo) or `[` (attribute). (→ Selector Rules)
* Explicitly declare a compound selector when simultaneous pseudo-class states set the same property. (→ Selector Rules)
* Compose with arrays; the right side always wins. (→ Core Usage)

**NEVER:**

* Pass a raw object to `sx`, e.g. `sx={{ color: 'red' }}`. (→ Forbidden Patterns)
* Call `css.create()` inside a component body. (→ Forbidden Patterns)
* Use the `&` self-reference character. (→ Selector Rules)
* Use a combinator (`>`, `+`, `~`, a space) outside a functional pseudo-class. For parent-state or descendant styling, reach for `css.marker()` / `css.extended()` first. (→ Selector Rules, Advanced APIs)
* Use class-name keys such as `.title` — style child elements directly. (→ Selector Rules)
* Nest a pseudo-selector inside another pseudo-selector — write `':hover::before'` as one key. (→ Selector Rules)
* Nest a media/container query inside a pseudo-selector. The reverse (pseudo inside media) is allowed once. (→ Selector Rules)
* Mix `className` and `sx` on the same element. (→ Forbidden Patterns)
* Merge `css.props()` output with the inline `style` prop. (→ Dynamic Styling)


* Join `css.props()` output with other class names, including another `css.props()` result passed through `className`, or pass it to a function such as `clsx` or `css.props()`. Pass every style to one `css.props()` call. (→ Forbidden Patterns)
* Read a definition from a namespace import by string key, destructuring or a rest element, or pass the namespace as a whole. Read it by name, as in `tokens.blue`. (→ Forbidden Patterns)
* Read a definition in an argument to a function key. Read it inside `css.create()`. (→ Dynamic Styling)

## Mental Model

- `css.create()` is compiled at build time into runtime class maps; CSS is extracted into a stylesheet.
- `sx` on an element compiles to a spread of `css.props(...)`, which merges styles at runtime and supplies `className` and any CSS variables on `style`.
- Compose arrays with right-wins precedence. Style values can pass through props, context, variables, and other packages before reaching an element.
- Import from `@typedcss/css`. The shared authoring API makes migration to Plumeria possible; its compiler has stricter component-boundary rules.

## Core Usage [#core-usage]

Define styles at module top level with `css.create()`, bind them with `sx`:

```tsx
import * as css from '@typedcss/css';

const styles = css.create({
  container: {
    display: 'flex',
    padding: '16px',
  },
  active: {
    backgroundColor: 'blue',
  },
});

export const MyComponent = ({ isActive }) => {
  return (
    <div sx={[styles.container, isActive && styles.active]}>
      Hello TypedCSS
    </div>
  );
};
```

**Right-wins composition.** `sx` accepts arrays, ternaries, and conditional expressions. The right-most style always takes precedence: above, `styles.active` overrides `styles.container` when `isActive` is true. `css.props()` follows the same rule. Within a single style, do not rely on source order to resolve overlapping pseudo-class states; declare their compound selector explicitly (see Selector Rules).

**Cross-file imports.** Import compiled styles from other files as runtime values. Keep `@typedcss/css` imported in files using `sx` so the integration can process them.

**Definitions from a package.** Share compiled class maps as runtime exports.

**Components from a package.** Pass `css.Style` through props and merge it on the element with `sx` or `css.props()`.

**Runtime imports.** Imports of compiled class maps and runtime helpers remain when used.

## Forbidden Patterns [#forbidden-patterns]

Never generate these patterns. They break static analysis or cause runtime errors.

**Passing an object directly to `sx`:**

```tsx
<span sx={{ fontSize: '12px' }}>Small Text</span>
```

**Creating styles inside a component body:**

```tsx
export const BadComponent = ({ dynamicColor }) => {
  const dynamicStyles = css.create({
    dynamic: {
      color: dynamicColor,
    },
  });
  // ...
};
```

**Mixing `className` and `sx` on the same element:**

```tsx
<span className="global-class" sx={styles.base}>Text</span>
```

**Joining `css.props()` output with other class names:**

```tsx
// Box.tsx
export const Box = ({ className }: { className?: string }) => (
  <div className={css.props(styles.base) + ' ' + className} />
);

// Parent.tsx
<Box className={css.props(styles.blue)} />
```

Strings from separate calls are not merged, so which rule wins depends on stylesheet order. Receive a `css.Style` prop and pass it to the same call instead, e.g. `css.props(styles.base, style)`. (→ Styling Custom Components)

**Reading a definition from a namespace import by anything but its name:**

```tsx
import * as tokens from './tokens';

const { styles } = tokens;

<div sx={tokens['styles'].card} />
```

Every use of a definition is written in place at build time, so the compiler has to see which one is read. `tokens.styles.card` compiles as `import { styles } from './tokens'` does. A string key, destructuring, a rest element or passing `tokens` as a whole stops the build.

**Complex JS expressions in style values.** Only simple ternary operators are allowed, and only when necessary. Never put complex logic or function calls inside style values.

## Selector Rules [#selector-rules]

TypedCSS supports nesting for pseudo-classes, pseudo-elements, and attribute selectors — under strict rules:

* **NO `&`.** TypedCSS does not use the `&` self-reference character.
* **Nested keys MUST start with `:` or `[`.** Pseudo-classes/elements start with `:`; attribute selectors start with `[`.
* **Combinators only inside a functional pseudo-class.** `>`, `+`, `~` and the descendant space are rejected anywhere else. `:has()`, `:is()` and `:where()` are accepted, and a combinator inside one (e.g. `':has(> img)'`) is the escape hatch for markup you do not write. For parent-state or descendant styling, prefer the paired `css.marker()` / `css.extended()` APIs (see Advanced APIs): they name no DOM path, so moving an element does not break them.
* **NO class-name keys.** Keys like `.title` are not supported. Apply TypedCSS styles directly to child elements instead.
* **NO pseudo inside pseudo.** Write a compound pseudo-selector as one key, e.g. `':hover::before'`.
* **NO same-name functional pseudo-class nesting, except `:not()`.** `':is(:where(:is(.a)))'` stops the build; different names can nest, and `':not(:not(.a), .b)'` is allowed. A key cannot nest parentheses deeper than 16 levels or hold a stray quote.
* **Declare overlapping states explicitly.** Pseudo-classes such as `:hover`, `:focus`, and `:active` can match simultaneously. When two states set the same property, declare their compound selector with the value the intersection should take. If they set different properties, no compound selector is needed. Functional pseudo-classes count too: `:nth-child(even)` and `:hover` setting the same property need the compound `':nth-child(even):hover'`.
* **Media/container query nesting is one-directional.** A pseudo-selector may be nested inside a media/container query exactly once. The reverse — a media/container query inside a pseudo-selector — is forbidden and causes compiler/type errors.

```tsx
const styles = css.create({
  button: {
    padding: '16px',
    backgroundColor: 'white',
    // VALID: Pseudo-classes and elements (starts with :)
    ':hover': {
      boxShadow: '0 4px 12px rgba(0,0,0,0.1)',
    },
    ':active': {
      boxShadow: '0 1px 4px rgba(0,0,0,0.2)',
    },
    // VALID: :hover and :active can match together; the intersection gets its own value
    ':hover:active': {
      boxShadow: '0 2px 6px rgba(0,0,0,0.3)',
    },
    '::before': {
      display: 'block',
      content: '""',
    },
    // VALID: Attribute selectors (starts with [)
    '[data-active="true"]': {
      borderColor: 'blue',
      borderStyle: 'solid',
      borderWidth: '2px',
    },
    // VALID: Pseudo-selector nested inside a media query (allowed once)
    '@media (max-width: 768px)': {
      padding: '8px',
      ':hover': {
        boxShadow: 'none',
      },
    },
  },
});

// INVALID: media query nested inside a pseudo-selector
const badStyles = css.create({
  button: {
    ':hover': {
      '@media (max-width: 768px)': {
        backgroundColor: 'blue',
      },
    },
  },
});
```

## Dynamic Styling [#dynamic-styling]

### Function keys [#function-keys]

For dynamic values (which would normally require React's inline `style` prop), define a **function key** in `css.create()`. Function keys compile to CSS variables — so unlike inline styles, they fully support `@media` and `@container` queries:

```tsx
const styles = css.create({
  palette: (color: string) => ({
    backgroundColor: color,
    // Media/container queries work on dynamic styles
    '@media (max-width: 600px)': {
      backgroundColor: 'blue',
    },
  }),
});

// Usage: <div sx={styles.palette(color)} />
```

An argument reaches the output as written. A TypedCSS definition read there, as in `styles.palette(tokens.blue[500])`, is not compiled and has no value at runtime. Read it inside `css.create()` instead.

### Bracket notation (variants) [#bracket-notation-variants]

The `css.variants()` API has been removed in favor of standard bracket notation (`styles[variant]`). Bracket notation selects a compiled style map at runtime:

```tsx
import * as css from '@typedcss/css';

// 1. Define variants in a dedicated, minimal css.create()
const sizeStyles = css.create({
  small: {
    fontSize: '12px',
  },
  medium: {
    fontSize: '16px',
  },
  large: {
    fontSize: '20px',
  },
});

// 2. Type the variant (string literal union or keyof typeof)
type Size = keyof typeof sizeStyles;

interface ButtonProps {
  size: Size;
  children: React.ReactNode;
}

// 3. Resolve dynamically with bracket notation
export const Button = ({ size, children }: ButtonProps) => {
  return <button sx={sizeStyles[size]}>{children}</button>;
};
```

Best practices:

* **Keep variants focused.** Group related variants for clarity. Bracket notation selects their runtime class maps.
* **Variant keys are selector-parsed: no spaces.** Every key in a `css.create()` — a variant key included — is read as a selector, so a key must not contain a space or combinator characters; a space is a descendant combinator and stops the build (`no-combinator`). When a display label contains a space, use a slug key and keep a label map for rendering: e.g. the status "On leave" becomes the key `onLeave`, with `const statusLabels = { active: 'Active', onLeave: 'On leave', offline: 'Offline' }`.
* **Local variable assignment is supported.** `const currentStyle = sizeStyles[size]; <div sx={currentStyle} />` works with runtime class maps.

### `css.props()` returns element props

`css.props()` merges class maps at runtime and returns `{ className, style }`. Spread the result onto an element. Function keys are supported: their CSS variables are passed through `style`. Prefer `sx` for the API shared with Plumeria.

## Advanced APIs [#advanced-apis]

### `css.marker()` and `css.extended()` (paired descendant styling) [#cssmarker-and-cssextended-paired-descendant-styling]

These paired APIs enable context-aware styling (e.g. styling a child when the parent is hovered) without naming a DOM path:

* **`css.marker(id, pseudo)`** — sets a CSS variable marker on the parent when the pseudo state is active. MUST be spread into the parent style: `...css.marker(...)`.
* **`css.extended(id, pseudo)`** — applies styles to descendants while the linked marker is active. Used as a computed key: `[css.extended(...)]`.

```tsx
import * as css from '@typedcss/css';

const styles = css.create({
  parent: {
    // 1. Set a marker with the unique id 'card' for the ':hover' state
    ...css.marker('card', ':hover'),
    padding: '24px',
    borderColor: '#ccc',
    borderStyle: 'solid',
    borderWidth: '1px',
  },
  child: {
    transition: 'color 0.3s ease',
    // 2. React to the 'card' marker being active
    [css.extended('card', ':hover')]: {
      color: 'blue',
      // Further pseudo-classes can be nested here
      ':hover': {
        color: 'darkblue',
      },
    },
  },
});

export const Card = () => {
  return (
    <div sx={styles.parent}>
      <span sx={styles.child}>Hover parent to make me blue!</span>
    </div>
  );
};
```

At build time this compiles to an atomic container style query (`@container style(--x1f9k2q1-card-hover: 1)`) — zero runtime overhead, zero dependency on DOM hierarchy.

### `css.createStatic()` [#csscreatestatic]

Defines static variables (such as media query strings) that are inlined at build time, typically used as computed keys in `css.create()`:

```tsx
import * as css from '@typedcss/css';

export const breakpoints = css.createStatic({
  xs: '@media (max-width: 480px)',
  sm: '@media (max-width: 640px)',
  md: '@media (max-width: 768px)',
  lg: '@media (max-width: 1024px)',
});

export const styles = css.create({
  container: {
    [breakpoints.sm]: {
      padding: 16,
    },
    [breakpoints.lg]: {
      padding: 32,
    },
  },
});
```

A numeric key, as in a color scale, is quoted: `'500': '#3b82f6'`. An unquoted number stops the build. Read it as `blue[500]` or `blue['500']`.

### `css.createTheme()` [#csscreatetheme]

Defines scoped CSS variables for themes. First argument: the selector that activates the theme. Second argument: an object of `{ default, theme }` value pairs. Generated variable names are prefixed with a unique hash, so name collisions are impossible. Theme values are only compiled when actually used in a styling block.

```tsx
import * as css from '@typedcss/css';

// Class-based theme
export const theme = css.createTheme('.dark', {
  text: {
    default: '#333',
    theme: '#eaeaea',
  },
  background: {
    default: 'white',
    theme: 'black',
  },
});

// Attribute selectors and media queries are also supported:
// css.createTheme('[data-theme="dark"]', { ... });
// css.createTheme('@media (prefers-color-scheme: dark)', { ... });
```

### `css.keyframes()` [#csskeyframes]

Generates a unique `@keyframes` animation name (a hash inlined at build time) for use inside style rules:

```tsx
import * as css from '@typedcss/css';

const fadeIn = css.keyframes({
  from: {
    opacity: 0,
  },
  to: {
    opacity: 1,
  },
});

const styles = css.create({
  card: {
    transition: 'transform 0.3s ease',
    ':hover': {
      animationName: fadeIn,
      animationDuration: '0.5s',
    },
  },
});
```

### `css.viewTransitionClass()` [#cssviewtransitionclass]

Generates a unique `view-transition-class`, accepting animation definitions (`group`, `imagePair`, `new`, `old`) to customize View Transitions. Pass it to the `default`, `enter`, `exit`, `update` or `share` prop of React's `<ViewTransition>`, or set it with `viewTransitionClass` in `css.create`. The rules are emitted only for those two uses, so pass it to `<ViewTransition>` directly rather than through a wrapper component:

```tsx
import * as css from '@typedcss/css';

const fadeIn = css.keyframes({
  from: {
    opacity: 0,
  },
  to: {
    opacity: 1,
  },
});

const fadeOut = css.keyframes({
  from: {
    opacity: 1,
  },
  to: {
    opacity: 0,
  },
});

const longCrossFade = css.viewTransitionClass({
  old: {
    animationName: fadeOut,
    animationDuration: '1.2s',
  },
  new: {
    animationName: fadeIn,
    animationDuration: '1.2s',
  },
});

// React usage:
// <ViewTransition default={longCrossFade}>...</ViewTransition>
// <ViewTransition name={`photo-${id}`} share={longCrossFade}>...</ViewTransition>
```

### `css.varType()` [#cssvartype]

Registers a typed custom property with `@property` and returns its name. Use it as a key to set the value and inside `var()` to read it. `initialValue` is required for every `syntax` but `'*'`, and must not depend on where it is used (no `em`, `rem`, container units or `var()`):

```tsx
import * as css from '@typedcss/css';

const angle = css.varType({
  syntax: '<angle>',
  initialValue: '0deg',
});

export const styles = css.create({
  ring: {
    background: `conic-gradient(from var(${angle}), red, blue)`,
    transition: `${angle} 0.6s ease`,
    ':hover': {
      [angle]: '180deg',
    },
  },
});
```

### `css.positionTry()` [#csspositiontry]

Defines an `@position-try` rule and returns its dashed name for `positionTryFallbacks`. It only accepts `positionAnchor`, `positionArea`, inset, margin, sizing and self-alignment properties:

```tsx
import * as css from '@typedcss/css';

const above = css.positionTry({
  positionArea: 'top',
  marginBottom: 8,
});

export const styles = css.create({
  tooltip: {
    position: 'absolute',
    positionAnchor: '--trigger',
    positionArea: 'bottom',
    positionTryFallbacks: `${above}, flip-inline`,
  },
});
```

## Styling Custom Components [#styling-custom-components]

Use `sx` on an element or accept a `css.Style` prop on a custom component. Styles merge at runtime on the element.

> **Core principle**: `Style` values are runtime class maps. They can pass through multiple component boundaries.

### Pattern 1: Direct `sx` inside the component [#pattern-1-direct-sx-inside-the-component]

The component imports its own styles and applies them internally. Simplest pattern — fully self-contained:

```tsx
import React from 'react';
import * as css from '@typedcss/css';

const styles = css.create({
  button: {
    padding: '10px',
    color: '#fff',
    cursor: 'pointer',
    backgroundColor: 'navy',
    borderColor: 'currentColor',
    borderStyle: 'none',
    borderWidth: 'medium',
    borderRadius: '4px',
  },
});

export const Button = ({ children }: { children: React.ReactNode }) => {
  return (
    // The compiler transforms sx into a css.props() spread here
    <button sx={styles.button}>
      {children}
    </button>
  );
};

// Usage
<Button>Click me</Button>;
```

### Pattern 2: Passing a `Style` prop [#pattern-2-passing-a-style-prop]

A component can receive `css.Style` through `sx` or another prop, then apply it on an element or forward it to another component. Compose `[styles.text, styleArray]` so call-site styles override base styles.

```tsx
// --- Button.tsx ---
import React from 'react';
import * as css from '@typedcss/css';

type ButtonProps = {
  children: React.ReactNode;
  styleArray?: css.Style;
};

// base style
const styles = css.create({
  text: {
    fontSize: '12px',
  },
});

// Pass styleArray directly to the inner element's sx
export const Button = ({ children, styleArray }: ButtonProps) => {
  return <button sx={[styles.text, styleArray]}>{children}</button>;
};

// --- Usage (call site) ---
import * as css from '@typedcss/css';
import { Button } from './Button';

const styles = css.create({
  primary: {
    padding: '10px',
    color: '#fff',
    backgroundColor: 'navy',
  },
  text: {
    fontSize: '24px',
  },
});

// styleArray merges with the base styles at runtime
<Button styleArray={[styles.primary, styles.text]}>Click me</Button>;
```

### Not a pattern: `className={css.props(...)}` on your own element [#not-a-pattern-classnamecssuse-on-your-own-element]

NEVER resolve styles with `css.props()` to apply them to an element your component renders. `sx` does the same job, and it also carries function keys, which `css.props()` cannot. Pattern 1 or Pattern 2 covers every element you render:

```tsx
// INVALID: sx applies these to an element you render
<button className={css.props(styles.text, styleArray)}>{children}</button>

// VALID
<button sx={[styles.text, styleArray]}>{children}</button>
```

`css.props()` is for the places `sx` cannot reach: a third-party component whose props have no `Style` type, a class name prop with another name such as `overlayClassName`, and templates that are not JSX (Vue, Svelte, Astro). The opt-in `@typedcss/no-use-in-jsx` lint rule reports every `css.props()` in JSX for projects that never need those.

### Plumeria migration compatibility

TypedCSS supports relaying a received `css.Style` through props, context, variables, and other components. This is valid TypedCSS code.

If you plan to migrate to Plumeria, we recommend applying each received style on an element rendered by that component instead of forwarding it through wrappers. Plumeria requires this shape for static compilation. Treat this as a migration recommendation, not a TypedCSS restriction.

### Summary [#summary]

| Pattern         | Compilation site     | Component's role             |
| --------------- | -------------------- | ---------------------------- |
| 1. Direct `sx`  | Inside the component | Self-contained styles        |
| 2. `Style` prop | Merged at runtime  | Receives and applies `Style` |

Applying a received style directly is recommended for Plumeria migration compatibility; forwarding it is supported in TypedCSS.

## Migrating from Tailwind CSS [#migrating-from-tailwind-css]

Tailwind's model and TypedCSS's do not map one-to-one. A utility-by-utility rewrite produces code that fails to compile, silently breaks, or reads like Tailwind reimplemented. Migrate one component at a time, under three rules.

**Resolve values from the compiled stylesheet, never from memory.** Utility values come from the project's `@theme`, not from a fixed table: `p-4` is `calc(var(--spacing) * 4)`, `text-sm` sets `font-size` *and* a paired `line-height`, and the color scale is whatever the project defines. Build the project and read the declarations out of the emitted CSS.

**NEVER carry a `--tw-*` variable chain across.** `shadow-lg` compiles to `--tw-shadow: …` plus `box-shadow: var(--tw-inset-shadow), …, var(--tw-shadow)`, and those variables hold a value only because Tailwind registers them with `@property`. Copied literally, the declaration is invalid and the shadow disappears. Resolve the chain to its final value instead.

**Where a compiled value is Tailwind's default, read it from `@typedcss/wind`.** The package holds the default theme of Tailwind CSS v4 as `css.createStatic` tokens, and each one compiles into the style that reads it, so nothing reaches the bundle. Install it with `pnpm i -D @typedcss/wind` and import it with `import * as t from '@typedcss/wind'`. It knows nothing of the project's `@theme`, so compare a token with the emitted CSS and keep the emitted value where the two differ. It generates no utility classes, so the key naming below still applies.

| Tailwind                    | `@typedcss/wind`                                                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `p-4`                       | `padding: t.spacing[4]`                                                                                                                     |
| `text-sm`                   | `fontSize: t.text.sm`, `lineHeight: t.textLineHeight.sm`                                                                                    |
| `font-medium`               | `fontWeight: t.fontWeight.medium`                                                                                                           |
| `bg-blue-500`, `text-white` | `backgroundColor: t.blue[500]`, `color: t.color.white`                                                                                      |
| `rounded-md`                | `borderRadius: t.radius.md`                                                                                                                 |
| `shadow-lg`                 | `boxShadow: t.shadow.lg`, which holds the resolved value                                                                                    |
| `md:`                       | ``[`@media (width >= ${t.breakpoint.md})`]``. The token is a length, so write the query around it; as a key on its own it produces no rule. |
| `animate-spin`              | `` animation: `${t.spin} ${t.animate.spin}` ``                                                                                              |

**Name keys after what the element is, not after the utilities it carried.** The class list is the input to the migration, not the output.

```tsx
// INVALID: Tailwind reimplemented — these names carry no more meaning than the class list did
const styles = css.create({
  hoverBgBlue500: {
    ':hover': {
      backgroundColor: '#3b82f6',
    },
  },
  px4: {
    paddingInline: '1rem',
  },
});

// VALID: One key per thing the component has
const styles = css.create({
  submitButton: {
    paddingInline: '1rem',
    backgroundColor: '#2563eb',
    ':hover': {
      backgroundColor: '#3b82f6',
    },
  },
});
```

**Three variants need restructuring rather than translation.** Breakpoints (`md:`) and `data-*` variants map directly, to `@media` and attribute-selector keys. `dark:` depends on the project: it is `@media (prefers-color-scheme: dark)` by default, but `@custom-variant dark` commonly redefines it as a `.dark` class selector — which belongs in the restructuring set below, not the direct one. Check the compiled output before assuming which.

| Tailwind                | Compiles to                               | Write instead                                                                                                                                           |
| ----------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hover:`, `focus:`      | `&:hover { @media (hover: hover) { … } }` | `':hover': { … }`, dropping the `@media (hover: hover)` wrapper — TypedCSS forbids a query inside a pseudo. The styles then apply on touch devices too. |
| `group-*`, `peer-*`     | `&:is(:where(.group):hover *)`            | `css.marker()` on the parent and `css.extended()` on the descendant. The `.group` / `.peer` class disappears.                                           |
| `space-x-*`, `divide-*` | `:where(& > :not(:last-child))`           | The margin or border applied to the children directly — a child combinator is only accepted inside a functional pseudo-class.                           |

### `tv()` and `twMerge()` [#tv-and-twmerge]

| Tailwind Variants  | TypedCSS                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `base`             | Static keys in the component's own `css.create()`                                                                            |
| `variants`         | One dedicated `css.create()` per variant group, read with bracket notation (keep these calls minimal — see Bracket notation) |
| `defaultVariants`  | Default parameter values                                                                                                     |
| `compoundVariants` | An explicit condition in the `sx` array                                                                                      |
| `slots`            | One `css.create()` per element, not one call carrying every slot                                                             |

**An external `className` override becomes a `Style` prop, not a `className`.** `twMerge(button(...), className)` exists to let the call site win; Pattern 2 does the same job, because array position is right-wins. **NEVER** resolve the override away, force it through `css.props()`, or change the component's public API to avoid the mixing rule.

**NEVER guess a class name that was built at runtime.** A template literal or a value read from props or state is not statically knowable. Leave the component on Tailwind and report it; a guessed utility compiles and is silently wrong.

```tsx
// --- Before ---
const button = tv({
  base: 'inline-flex rounded font-medium',
  variants: {
    size: { sm: 'h-8 px-3 text-sm', lg: 'h-12 px-6 text-lg' },
    tone: { primary: 'bg-blue-500 text-white', danger: 'bg-red-500 text-white' },
  },
  compoundVariants: [{ size: 'lg', tone: 'primary', class: 'shadow-lg' }],
  defaultVariants: { size: 'sm', tone: 'primary' },
});

<button className={twMerge(button({ size, tone }), className)} />;

// --- After (values resolved from the project's compiled CSS, not recalled) ---
const styles = css.create({
  base: {
    display: 'inline-flex',
    fontWeight: 500,
    borderRadius: '4px',
  },
  lgPrimary: {
    boxShadow: '0 10px 15px -3px rgb(0 0 0 / 0.1)',
  },
});

const sizeStyles = css.create({
  sm: {
    height: '32px',
    paddingInline: '12px',
    fontSize: '14px',
  },
  lg: {
    height: '48px',
    paddingInline: '24px',
    fontSize: '18px',
  },
});

const toneStyles = css.create({
  primary: {
    color: '#fff',
    backgroundColor: '#3b82f6',
  },
  danger: {
    color: '#fff',
    backgroundColor: '#ef4444',
  },
});

  size?: keyof typeof sizeStyles;
  tone?: keyof typeof toneStyles;

};

  <button

      toneStyles[tone],
      size === 'lg' && tone === 'primary' && styles.lgPrimary,

```

## Testing [#testing]

**NEVER stub `@typedcss/css`.** It publishes runtime helpers and types; style definitions still require the compiler transform. A `moduleNameMapper` entry or a hand-written mock makes the suite run, but every class name it produces is invented, so the test says nothing about the styles. If a runner cannot resolve the package, that is the signal to test a different layer, not to fake the package.

**NEVER assert a generated class name in a component test.** `xvdv6o3r` is one property-value pair, hashed. Adding a property to the style breaks every test that spelled the old list out. Assert what the component renders, holds, or branches on.

**To test component behavior, put the transform in the runner's module pipeline.** This is the only layer that needs it. Vitest takes the plugin in its config:

```ts
export default defineConfig({
  plugins: [react(), typedcss.vite()],
  test: { environment: 'jsdom' },
});
```

Jest takes `@typedcss/swc-jest` in place of `@swc/jest`, `ts-jest` or `babel-jest`; SWC options stay in `.swcrc` or beside the transformer:

```js
module.exports = {
  testEnvironment: 'jsdom',
  transform: { '^.+\\.(t|j)sx?$': '@typedcss/swc-jest' },
};
```

**jsdom applies no stylesheet.** `document.styleSheets` is empty and `getComputedStyle` returns initial values. A test there can see which classes were attached, never what they do. Anything about the cascade — specificity, `@media`, `marker` with `extended` — belongs in an end-to-end test against a real browser.

## Toolchain Notes [#toolchain-notes]

**Setup.** Do not write the configuration by hand. `npx @typedcss/init` detects the package manager and the bundler, installs the packages, writes `typedcss.d.ts` and the bundler config, extends the ESLint flat config, and on esbuild and Bun puts `typedcss-lint --` in front of the `build` script. The other bundler plugins lint the build themselves. It shows the plan before it writes, `--dry-run` stops at the plan, and `--yes` takes every default without asking, which is what makes it usable without a TTY. A project that is already set up reads as done and nothing is written.

**Compiler expectations.** The compiler statically extracts `css.create()` calls, which is why they MUST sit at module top level. Prefer direct, clearly defined references — indirect variable references may be unanalyzable.

**ESLint guarantees.** `@typedcss/eslint-plugin` enforces TypedCSS's rules. Treat its errors as blocking, and its warnings (such as `no-order-dependent-overlap`) as defects to resolve rather than noise. It checks:

* **CSS property value validation** — invalid values are caught at lint time.
* **Property sort order** — one canonical order is enforced; the full order is specified under **Property order** below.
* **Property formatting** — one property per line, with no empty lines between properties; see **Property formatting** below.
* **Unused style detection** — unused styles are flagged automatically.

Follow the plugin's rules as documented in its `README.md`.

After every plain property, nested keys follow in this order: pseudo selectors (`:hover` and the like), then `&` selectors, then `@media` and `@container` blocks. A property that does not appear in the list sorts after the listed properties and before the selectors.

**Border shorthands.** Never write `border`, `borderBlock`, `borderInline`, `borderTop`, `borderRight`, `borderBottom`, `borderLeft`, `borderBlockStart`, `borderBlockEnd`, `borderInlineStart` or `borderInlineEnd`. A border shorthand always sets a width, a style and a color at once, even when the value names only one of them, and `expand-border-shorthands` rejects it. Write the three declarations it stands for instead — `borderColor`, `borderStyle`, `borderWidth`, or the per-side forms such as `borderTopColor`, `borderTopStyle`, `borderTopWidth`. For example, `border: 'none'` becomes:

```ts
borderColor: 'currentColor',
borderStyle: 'none',
borderWidth: 'medium',
```

The per-side forms expand into their own three longhands, and the axis forms (`borderBlock`, `borderInline`) expand the same way into `borderBlockColor`, `borderBlockStyle`, `borderBlockWidth` and their `borderInline` counterparts. For example, `borderTop: '1px solid #d1d5db'` becomes:

```ts
borderTopColor: '#d1d5db',
borderTopStyle: 'solid',
borderTopWidth: '1px',
```

A component the value does not name takes its initial value — width `medium`, style `none`, color `currentColor` — and is still written out, so `borderInlineStart: '2px dashed'` becomes:

```ts
borderInlineStartColor: 'currentColor',
borderInlineStartStyle: 'dashed',
borderInlineStartWidth: '2px',
```

**Property formatting.** In a style object, every property sits on its own line, and there are no empty lines between properties. `format-properties` rejects both a shared line and a blank line, and a warning stops the build, so expand compact objects when you write them. A variant map entry such as:

```ts
design: { color: '#1d4ed8', backgroundColor: '#dbeafe' },
```

is written:

```ts
design: {
  color: '#1d4ed8',
  backgroundColor: '#dbeafe',
},
```
